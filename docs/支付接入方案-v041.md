## 这份文档怎么读

每一格都标了 **实读** 还是 **未读到**：

- **实读** = 本轮真的把那一页取下来读到了那句话；
- **未读到** = 页面在商户后台之后、或正文由 JS 渲染（`WebFetch` 只拿到标题）。
  **未读到的格子里不写任何数字**——写上去的费率既没有出处，也不知道是哪一年的。

这条纪律比文档写得漂亮重要：一份「凭记忆写的费率」与一份「从官方页读到的费率」

## owner 裁决（2026-08-04）：两条硬边界

1. **NEVER 自建支付系统**——只做「跳转到**对方页面**付款 + 收结果回调」。
   四家全部满足这一条：用户输入支付凭据的那一屏都在收银台一侧，我们拿不到、也不该拿到。
2. **NEVER 存储卡号**——不碰卡号 = 不进 PCI 合规面。
   四家的托管形态下，卡号从不经过我们的服务器。

配套两条（DEC-024 原文）：**金额恒服务端计算**，NEVER 信前端传来的价格；
计费基准 = 每次对话实际消耗的 API 用量 × 配置里的单价。

## 四家的形态差异（这才是选型的依据）

**三家是收单方，一家不是。** 微信支付、支付宝、PayPal 都能直接收钱、直接回调；
**Apple Pay 不是收单方**——官方原话让你「用支付服务商的 Apple Pay SDK」。
所以 Apple Pay 不能与前三家并列比较：它是**前端的一种付款方式**，
背后仍要挂一个 PSP，费率与结算全看那个 PSP。

**回调的严实程度不同。** 微信的回调报文是**加密的**（AES-256-GCM），
除验签外还要解密；PayPal 的回调是明文 + 签名头，可本地自算也可回调它的验签端点；
支付宝是表单 POST + RSA 验签，且要求商户回校 `out_trade_no` / `total_amount` /
`seller_id` / `app_id` 四项——**验签通过不等于这笔是给你的**，那四项才回答「是不是给你的」。

**重试策略差一个量级。** 微信 15 次 / 最长跨约 26 小时；PayPal 25 次 / 3 天。
两家都要求商户端**幂等**——DEC-024 的「扣费 MUST 带幂等键，同一笔重放只扣一次」
正是冲着这件事。

## 接入优先级建议（中国用户 / 海外用户各一条）

### 中国用户：先接**微信支付 Native/JSAPI**

**理由**三条：

1. **回调规格本轮读全了**——加密方式、四个验签头、应答格式、5 秒时限、15 次重试表
   全部有出处（上表微信「回调机制」那一格是实读）。接线时不用再猜；
2. 本产品是**网页应用**，JSAPI（微信内）+ Native 扫码（微信外）覆盖得到；
3. 支付宝的接口与回调本轮**正文没读到**（JS 渲染），接线前还要再查一轮——
   把它排第二不是因为它差，是因为**我们对它的了解还不够动手**。

**需要 owner 提供**：营业执照、法人身份证、对公银行账户（开户后拿到**商户号** mchid）、
APIv3 密钥与商户 API 证书。**这几样都属红线**（付费网关开通与真实商户密钥），
本卡 NEVER 自行申请。

### 海外用户：先接 **PayPal 标准 Checkout**

**理由**三条：

1. **费率是四家里唯一本轮读到确数的**：3.49% + 0.49 USD（境内）、跨境 +1.50%、
   货币转换 4.00%（部分 3.00%）、月费 "No fee"。定价能算得出来；
2. **注册门槛最低**：商务账户即可，无月费无开通费——K7/K8 定价未定期间最合适；
3. **回调规格也读全了**（两种验签、四个头、2xx 应答、3 天 25 次重试）。

**需要 owner 提供**：PayPal 商务账户、应用的 `client_id` 与 `client_secret`、
Webhook ID。同属红线，本卡 NEVER 自行开通。

### Apple Pay：**不单独接，跟着 PSP 走**

它不是收单方。等海外那条线选定 PSP 之后，用那个 PSP 的 Apple Pay SDK 打开即可；
届时需要 owner 提供 Apple Developer 账号、Merchant ID 与商户身份证书、域名验证。
**现在不做**：没有 PSP 的 Apple Pay 是个接不上收单的按钮。
