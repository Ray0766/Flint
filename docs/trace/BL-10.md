## 3. 已经有一把了，为什么还要一把

`eval/lineage.py`（M1-039）能算准确率，但与 S4 的出口断言对不上三处：

| 差 | 后果 |
|---|---|
| **没有样本量闸** | S4 写的是「≥90%（**50 簇**）」；它拿 3 簇也报 100% 并 exit 0——**小样本算出的数字长得与真判定一模一样** |

| **口径没写死** | 少一个事件怎么算、标注里有实际没有怎么算——不写清，下次量的数与这次不可比 |

所以本卡交的是**尺**不是门：`main` **恒返回 0**，源码面也禁掉 `return 1` / `exit(1)`。

## 4. 口径（acceptance③，逐条有用例）

| 规则 | 为什么 | 用例 |
|---|---|---|
| 一次「正确」= (day, kind) **全序列逐项相等** | —— | `test_a_cluster_matches_only_when_the_whole_timeline_matches` |
| **全或无**：少一个/多一个都算错 | 按事件计分会让「漏了一次 split」看起来只丢一点点，而血缘是时间线，错一处后面全错位 | `test_one_missing_event_makes_the_whole_cluster_wrong`、`test_one_extra_event_also_makes_it_wrong` |
| **顺序敏感** | 先分裂后合并与先合并后分裂是两件事 | `test_the_order_matters` |
| 标注有、实际无 → **计入分母** | 跳过它分母变小、准确率虚高，而「压根没产出这个簇」是最严重的一种错 | `test_a_labelled_cluster_that_is_missing_counts_in_the_denominator` |
| 实际有、标注无 → 不计分，但**报条数** | 它可能说明标注集不全 | `test_an_unlabelled_cluster_is_reported_but_not_scored` |
| 一律按字符串比 | 数值化或按日期对象比会在时区与格式上引入第二套口径 | （写在 docstring） |

「**够样本量**」与「**达线**」分两个属性报（`judgeable` / `meets_line`），
NEVER 混成一个「通过」——`test_being_judgeable_is_not_the_same_as_passing` 守着。

## 5. 全仓实跑：**S4 的出口断言今天评不了**（重要）

```
$ python harness/lineage_accuracy.py --labels assets/labels.yaml --dsn …/flint
血缘准确率 0/50 = 0.00%   （**report_only**）
  样本 50 够 50；未达线（参考，判定归 owner）
EXIT=0

$ python -m eval.lineage --labels assets/labels.yaml --dsn …/flint     # 交叉核对
lineage accuracy: 0/50 = 0.00%
expected events by kind: continued=914, dormant=5, new=50, revived=5
```

**两把尺子给出同一个数**——不是某一把算错了。

根因是数据不是代码：

```
lineage_audit：1027 行，**只有 7 天**（2026-06-29 .. 2026-07-05）
labels.yaml  ：window 2026-06-24 .. 2026-07-23（**30 天**），dormant_after_days: 14
```

7 天的库**结构上不可能**产出 dormant/revived（那需要 14 天静默）。
**金标 50 簇齐了，缺的是把那 30 天真的回放进某个库。**

0% 很容易被误读成「血缘算法坏了」——它不是：`flint/lineage/` 四阶段各有用例且全绿。
登记在 `docs/blocked/LINEAGE-GOLD-REPLAY-MISSING.md`（含实测、根因、三步修法）。
**没有去灌库**（资源触点 + 可能触真实源抓取，§7 红线），**没有替 owner 判定**。
