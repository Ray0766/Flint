# `CN-06` 收尾：两次浏览器探针对同一屏读出两个日期

**状态** closed · 2026-08-11 · `CN-06`

## 现象

灌库之后**数据确实在**：

```
heat_points max(day)                     = 2026-08-10
GET /plaza/hot?day=2026-08-10&region=CN  → 125 簇，真词面
```

两次浏览器探针**结论不同**：

| 探针 | 读到 |
|---|---|
| `CN-06` 自己那次（`networkidle` + 2500ms） | `正在看 2026-08-10 的热点`（截图 `.ui-probe/cn06-plaza.png`） |
| `test_cn03_preflight.py::test_the_plaza_lands_on_the_newest_day_with_data` | `正在看 2026-07-05 的热点` |

## 这条红**有主**，且它是对的

它量的是 `CN-03` 那条产品：首屏不带 `?day=` 时**落在最新有数据的那一天**。
今天最新是 `2026-08-10`，而那条判据读到 `2026-07-05`——
**两次读同一屏得出两个答案，本身就是一个缺陷**，不管哪一次是对的。

## 三个待查方向（worker 未验，上下文用尽）

1. **Next.js dev server 的路由缓存**：两次探针间隔几分钟，
   前一次可能命中了灌库前的缓存，也可能是后一次命中；
2. **两个探针的等待点不同**：`CN-06` 那次等到 `networkidle` 再加 2500ms，
   `CN-03` 那条的 runner 等待条件更短——若倒退搜索是异步的，早读会读到起步值；
3. **倒退搜索的起点**：`DAY_LOOKBACK = 41` 从本机今天起走。
   本机与 UTC 今天此刻同为 2026-08-10，这一条**最不可能**，但没排除。

## 绕行现状

`CN-06` 的其余出口全部达成（四源真录、真词面上屏、署名带港区、置顶行如实跳过）。
**这一条红照实留着**，NEVER 靠改判据的等待时间去让它变绿——
那样只是把「两次读出两个答案」这件事藏起来。

---

## 关闭（`CN-06`）：**三个方向都不是，是探针在读缓存**

`_probe()` 的第一句是：

```python
if _ARTIFACT.exists():
    return json.loads(_ARTIFACT.read_text(encoding="utf-8"))
```

那份产物是 `CN-03` 那天写的——实测 mtime **`2026-08-09T16:08`**，
内容 `正在看 2026-07-05 的热点`。**这条判据根本没去探过屏**，
它读的是两天前的旧答案；而同一时刻手动探针读到的是 `2026-08-10`。

> **一把返回缓存答案的探针不是探针**：它红或绿都与屏上此刻的样子无关。

那句话原本想省的是「同一次 pytest 里多条判据各启一次浏览器」。
改成**会话内记忆**（模块级 `_MEMO`）：一次进程内只探一遍，
而**每次跑都重新去看一眼**。产物照旧写盘——它是给人看的证据与截图，不是答案。

删掉旧产物后重跑：`正在看 2026-08-10 的热点`，与手动探针一致，
`tests/v041/test_cn03_preflight.py` **18 passed**。

**没有去调等待时间**——那只会把「两次读出两个答案」这件事藏起来。
