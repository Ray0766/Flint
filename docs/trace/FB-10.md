## 3. 实况：代码层本来就是干净的

按卡面点名的六种形态扫 `web/` 的**代码层**（剥注释后）：

| 形态 | 实况 |
|---|---|
| 端点路径（`GET /deliverables/{id}/blocks`） | **零命中**（只在注释里出现，那是在解释实现） |

所以本卡真正的产物是**尺子**：让这些形态 NEVER 漂回来。

## 4. 唯一那处：`field_path` 保留，并显式登记为例外

`ProfileRef.field_path` 是**第三条出处通道**——它说的是「这个数字来自档案里的哪一项」。
删掉它就是删掉出处，与 acceptance④「诚实态相关的可见信息一条不删」直接冲突。
但它确实长得像 schema 字段名，所以**不能靠规则写得松来放过它**，
而要在尺子里**写明为什么放行**（`ALLOWED_FIELD_RENDERS` + 文件头一整段理由）。

**这条例外是承重的，不是装饰**——实测证明：把例外表清空之后，尺子当场抓出那一行：

```
✗ web/components/blocks/BlockView.tsx:46  [schema 字段名当正文]
  return <span data-profile-path={span.field_path}>{span.field_path}</span>;
EXIT=1
```

也就是说规则**真的覆盖到了**这个形态，是例外把它放行的，不是规则看漏了。
另配一条 `test_an_undeclared_field_name_render_is_still_caught`：例外只对 `field_path` 一个，
别的字段名照旧红——**否则「登记例外」就变成了一个谁都能钻的口子**。

## 5. 判据的三条边界（都是为了不误伤诚实态）

1. **只扫代码层**——注释里写 `POST /workbenches/{id}/edges` 是在解释实现，不是渲染它。
   本批**第六次**同一类问题（GAUGE-06 / FB-01 / FB-02 / FB-04 / FB-09 / 本卡），修法始终相同；
2. **`data-*` 属性不算**——那是取证与调试的落点（EYE-01 的 `--selector` 靠它定位、
   既有 BlockView 测试也靠它）。属开发面但**不显示给用户**，与「跑到屏上」是两回事；
3. **出处 id 本身不算**——`{c.citation_id}` 是引用通道的内容；FB-09 之后由 `DerefValue`
   换成人话，换不到时如实显示原 id，那是**诚实态**不是脚手架。
