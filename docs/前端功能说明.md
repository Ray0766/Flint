## 0. 给 UI 生成器（如 v0）的说明

本文档是功能规格，用于生成 UI。视觉风格由 owner 决定；以下为生成 UI 时需满足的功能约束（均为字段驱动的呈现规则，不涉及样式）：

1. **状态字段驱动呈现**：结论/主题的 `speculative`、block 的 `needs_review` 等状态字段为 true 时，界面显示对应的状态标记（降权/复核标），不作为确定结论呈现。
2. **引用与出处**：引用（`citation_id`）呈现为可点元素，点击展示出处（quote_span / 来源 url）。数字按其类型化出处分通道呈现（Fact / Price / Profile 三通道分别渲染，不合并为一种数字）。
3. **缺口/降级/判定状态**：`gap_notice`（留白）、`degraded`（降级生成）、`D_insufficient`（证据不足判定）、`disputed`（争议中）、`stale`（陈旧）等状态按数据如实显示。
4. **只读与零计算**：保护块（`locked ∨ author=="user" ∨ user_modified`）不含编辑控件；图表按后端提供的数据渲染，前端不做数值聚合/计算。

**使用方式**：第二节每个界面给出 **①本屏状态元素**（该屏需按字段呈现的状态标记）+ **②示例数据**（真实响应形状的样例 JSON，含非空状态样例：speculative=true 的主题、needs_review 的 block、D_insufficient 的 verdict 等），按示例 JSON 的键名/取值域渲染。第四节为这些状态字段的完整依据。

> 示例 JSON 的键名、取值域、结构与真实响应一致（照 API 总表/契约）；`message` 等自由文本字段为示意，可替换。

## 一、产品模型 + 核心用户旅程

### 产品模型（一句话）

Flint 把四热点源日更（google trends / weibo / github trend / arxiv）沉淀成热点簇 → 证据卡，让用户跨热点做关联假设（combo）→ 生成候选主题 → 对主题跑 Gate① 四分类可行性判定（全引用）→ 深度报告 → 计划书（受众分叉：给人看的五模板 / 给 AI 执行的 vibe_pack）→ 导出 → 支付。

**数据呈现原则**：每个结论附引用、每个数字标类型化出处、不确定/缺口/争议按数据标注、无法判定时输出 `D_insufficient` 及缺口清单。前端按这些状态字段的值呈现（字段依据见[第四节](#四字段驱动的状态呈现规则)）。

### 三个层次的数据

- **日更采集层**：`Cluster`（热点簇）+ `HeatPoint`（单源单日热度）+ `EvidenceCard`（证据卡）——广场/工作台读这层。
- **主题层**：`Origin`（入口，combo 是其一种）→ `TopicSeed`（种子，带 `hypothesis`）→ `Topic`（候选主题，带 `why_now`）→ `Project`（项目容器）。
- **产物层**：`Job`（作业）→ `VerdictResult`（Gate 裁决）/ `Deliverable`（报告/计划书/vibe_pack）→ `Block` 树（结构化正文，唯一真相）→ `FactsLedger`（跨产物事实账本）。

### 核心用户旅程（每步标现状 + 主端点）

| # | 步骤 | 用户动作 | 主端点 | 现状 |
|---|---|---|---|---|
| 1 | 热点广场 | 看当日热点主榜 + 弱信号早期轨 | `GET /plaza/hot?day=` | 【已建·已挂载】（正式版路由未建，仅 /demo 内） |

## 二、逐界面 / 功能

> 每个功能写：是什么 · 现状 · 后端端点+请求/响应形状 · 交互流(loading/SSE/错误/空/状态) · 未来接口缝。字段名逐字取自代码。

### 2.1 热点广场（hotness 主榜 + 弱信号轨）

- **是什么**：当日热点两轨——主榜（clusters，按综合热度分排序）+ 弱信号早期轨（weak_signals，小而在加速的语义新趋势，单列一轨，与主榜分开）。
- **现状**：端点【已建·已挂载】；前端 `PlazaView`【已建】但只活在 `/demo` 串联里，正式版 `/plaza` 路由未建（`web/app/` 下无此 page）。
- **后端端点**：`GET /plaza/hot?day=YYYY-MM-DD`（`flint/api/views.py:65`）
  - 请求：query `day`（唯一参数）。无 Header、无体。
  - 响应 200：`{ "day", "clusters", "weak_signals" }`
    - `clusters[]`（主榜）逐字键：`cluster_id, canonical_name, category_id, status, by_source, total_heat, hotness, hotness_components{velocity, accel, cross_count, multi_boost, novelty_factor, decay}`
    - `weak_signals[]`（弱信号轨）逐字键：`cluster_id, canonical_name, category_id, status, weak_score, agg, velocity, drift, burst_weight`
  - 错误：400 `VALIDATION_FAILED`（`day` 非 `YYYY-MM-DD`）。
- **交互流**：
  - loading：拉 `/plaza/hot` 时的加载态。
  - 空态：某天无数据 → `clusters=[]`、`weak_signals=[]`（如本地 2026-07-20 空；有数据日如 2026-07-04）。前端渲染"该日无热点"（非错误态）。
  - 排序/来源：排序由后端定（已按综合分排好），前端 `PlazaView` 零计算、不重排（`PlazaView.tsx:5` 注释）。`by_source` 为逐源分值（各 `source_id` 的 norm_score），按源分别展示。
- **未来接口缝**：主题层进广场（Q-009）——目前 `/plaza/hot` 只返回 `clusters + weak_signals`，无 topics；前端 i18n 已留占位串 `plaza.topic_deferred`=「主题」层 V1 不含，待 Q-009（`web/lib/i18n.ts:16`）。回接时若 owner 决定主题进广场，需扩 plaza 端点加 topics + 排序口径。
- **本屏状态元素**：
  - 弱信号轨（`weak_signals`）单列，与主榜 `clusters` 分开呈现。
  - 主榜按后端 `hotness` 综合分排序，前端不重排（零计算）。
  - `by_source` 按源分别展示各源分值。
- **示例数据**（`GET /plaza/hot?day=2026-07-04`）：
```json
{
  "day": "2026-07-04",
  "clusters": [
    {"cluster_id": "c-20260704-000", "canonical_name": "固态电池量产突破", "category_id": "cat-energy",
     "status": "active", "by_source": {"arxiv": 88.0, "ghtrend": 41.2, "gtrends": 30.5, "weibo": 22.0},
     "total_heat": 159.7, "hotness": 87.75,
     "hotness_components": {"velocity": 12.3, "accel": 4.1, "cross_count": 3, "multi_boost": 1.2, "novelty_factor": 0.8, "decay": 1.0}}
  ],
  "weak_signals": [
    {"cluster_id": "c-20260629-134", "canonical_name": "solid-state battery", "category_id": "cat-energy",
     "status": "active", "weak_score": 20.0, "agg": 6.4, "velocity": 20.0, "drift": 0.03, "burst_weight": 1.0}
  ]
}
```

### 2.2 工作台（证据卡）

- **是什么**：点某个簇后，看它的证据卡（关键词、信号旗标、头部链接）。
- **现状**：端点【已建·已挂载】；前端 `WorkbenchView`【已建】，仅在 /demo 内。
- **后端端点**：`GET /clusters/{cluster_id}/evidence-cards`（`views.py:154`）
  - 请求：路径参数 `cluster_id`。无体。
  - 响应 200：`{ "cluster_id", "evidence_cards" }`；`evidence_cards[]` 逐字键：`card_id, cluster_id, keyword_ids, flags, top_links`。
  - 空态：未知簇 → `evidence_cards: []`（非 404）。
- **交互流**：`flags`（`novelty|momentum|revival` 信号旗标）按数据展示；`top_links` 为外链，渲染为可点链接（`WorkbenchView.tsx`）。
- **未来接口缝**：关联假设持久化（Q-010）——工作台 i18n 已留占位 `workbench.hypothesis_deferred`（`i18n.ts:21`）。注：combo 的 `hypothesis` 数据层已落库（`origins`/`topic_seeds` 表）+ 创建端点已建（`POST /projects/combo`），但工作台读端点 `evidence-cards` 未 surface hypothesis 字段。回接时若要在工作台展示已建假设，需扩读端点。
- **本屏状态元素**：
  - `flags`（`novelty` / `momentum` / `revival`）按数据展示。
  - `top_links` 为外链，呈现为可点跳转。
- **示例数据**（`GET /clusters/c-20260704-000/evidence-cards`）：

     "keyword_ids": ["kw-solid-electrolyte", "kw-anode-free"],

### 2.3 combo 入口（关联假设建项）

- **是什么**：跨簇选 2~5 张证据卡 + 写一句关联假设 → 后端建 `Origin`→`TopicSeed`→ 编排生成 N 个候选主题 → 建 `Project`。
- **现状**：端点【已建·已挂载】；前端 `ComboEntryView`【已建】。
- **后端端点**：`POST /projects/combo`（`combo.py:78`）
  - 请求：Header `X-User-Id`（必需）；体 `ComboCreateRequest`（`schemas.py:87`）：`card_ids: list[str]`、`hypothesis: str`。
  - 响应 200：`ComboCreateResponse`（`schemas.py:97`）：`project_id: str`、`topic_ids: list[str]`、`degraded: bool`。
  - 错误：400 `VALIDATION_FAILED`（卡不存在/校验失败）；缺 Header/字段 → 422。
- **交互流**：
  - 前端硬校验：卡数 2~5（`COMBO_MIN=2/COMBO_MAX=5`，`topicClient.ts:45`）、hypothesis 非空——不合规禁用提交（`ComboEntryView.tsx:60`）。
  - loading：combo 走免费本地 qwen 生成，真机 ~秒级到十几秒；前端需生成中 loading 态。
  - `degraded`：`ComboCreateResponse.degraded: bool`，true 表示部分主题降级生成（本地模型降级兜底）。前端标注"部分降级生成"。
- **未来接口缝**：生产 combo 的 `{cards}` 强接地注入（A4）——`generate_topic` 已开 `cards_context` 可选形参，生产环接线待做。
- **本屏状态元素**：
  - 响应 `degraded == true` 时，标注「部分主题为降级生成」。
- **示例数据**（`POST /projects/combo` 响应，degraded=true 样例）：
```json
{"project_id": "proj-demo7c1", "topic_ids": ["topic-demo7c1-1", "topic-demo7c1-2", "topic-demo7c1-3"], "degraded": true}
```

### 2.4 主题列表 + 选主题

- **是什么**：看某项目下的候选主题、看单主题详情、选定一个主题。
- **现状**：端点【已建·已挂载】；前端 `TopicListView`【已建】。
- **后端端点**：
  - `GET /projects/{project_id}/topics`（`views.py:198`）→ `{ project_id, chosen_topic_id, topics }`（未知 project → `chosen_topic_id: null, topics: []`，非 404）。
  - `GET /topics/{topic_id}`（`views.py:190`）→ `{ topic: {...} }`（未知 → 404 `NOT_FOUND`）。
  - `topic` 逐字键：`topic_id, seed_id, one_liner, target_user_tag, form_factor_tag, why_now{claim, evidences[{event, event_date, citation_id}], speculative}, keyword_mapping`。
- **交互流**：
  - `why_now.speculative`：`bool`——true（evidences 为空）时前端把 why-now 标为「推测（无证据支撑）」并抑制溯源入口；false 时展示 `evidences[]`（每条 event + event_date + 可点 citation_id）。`TopicListView.tsx:30` 打 `data-speculative`、`:46-48` 打降权标。
  - `keyword_mapping` 前端可派生展示词（`topicKeywords`，`topicClient.ts:54`，纯前端派生）。
  - 选主题：`chosen_topic_id` 标识已选（`TopicListView` 切换按钮文案）。
- **未来接口缝**：`chosen_topic_id` 的写入（选定动作）目前经 analysis submit 的 `topic_id` 传参隐式驱动；无独立"设为已选"写端点（如需显式选定持久化，需新增）。
- **本屏状态元素**：
  - `why_now.speculative == true` 的主题显示推测/降权标记（如"推测·无证据支撑"），不呈现其溯源入口。
  - `speculative == false` 时展示 `evidences[]`，各条 `citation_id` 呈现为可点溯源。
  - `chosen_topic_id` 标识已选主题；未选/空态按数据呈现。
- **示例数据**（`GET /projects/proj-demo7c1/topics`，含一个 speculative=true 与一个 false）：

### 2.5 Gate 视图（四分类全字段）

- **是什么**：展示 Gate① 对某主题的可行性判定——`A_infeasible`（不可行）/ `B_red_ocean`（红海）/ `C_opportunity`（机会）/ `D_insufficient`（证据不足），含关键引用、依据事实、竞品清单、缺口清单。
- **现状**：端点【已建·已挂载】；前端 `GateView` 组件【已建·未挂载】——`GateView.tsx` 已建且已单测，但未被任何页面/DemoFlow import；/demo 的 gate 步只跳链到 `/jobs/{id}` 进度页，不渲染判定结果。即当前运行态 UI 里 Gate 结果无处显示，回接时需把 GateView 挂上。
- **后端端点**：`GET /jobs/{job_id}/verdict`（`views.py:176`）→ `{ "job_id", "verdict": {...} }`
  - `verdict` 逐字键（快照透传，来自 `flint/jobs/gate1.py:466-487`）：`verdict, all_satisfied, key_citation_ids, rationale_fact_ids, competitors[{name, url, strength, strength_signals, pricing}], constraints_checked, gaps[{missing_what, cause, suggested_sources, action, target_count, required_scope}]`

### 2.6 分析 Job + SSE 渐进（L1）

- **是什么**：发起分析后，用 Job 快照 + SSE 事件流实时看进度。

- **后端端点**：
  - `POST /projects/{project_id}/analysis`（`analysis.py:109`）：Header `X-User-Id`（必需）+ `Idempotency-Key`（可选）；体 `AnalysisSubmitRequest`：`keywords: list[str]=[]`、`locale: str="zh-CN"`、`budget_cny: float`（必填）、`topic_id: str|None`（带 topic_id → 从 Topic 派生 keywords）→ `{ job_id }`。

### 2.8 干预层（L2：lock / regenerate / dispute / evidence）

- **是什么**：对报告做四种干预——锁定块、章节再生成、争议某块/事实/引用、注入补充证据。
- **现状**：端点【已建·未挂载】；前端三个面板（`BlockInterventionPanel`、`EvidencePanel`、`InstructionRegenerateBox`）均【已建·未挂载】（grep 确认只被自己的测试引用，无 app 页面 import）。`/deliverables/[id]` 只挂 L0 只读的 `BlockTree`，旁边没有干预面板。回接时需新建一个"可干预的交付物页"把这三个面板 + 块内容组合。
- **权限**：所有干预需 `X-User-Id`；org 域需 `role ∈ {owner, admin}`，越权 403 `PERMISSION_DENIED`（`interventions.py:50`）。前端保护块门控唯一真相：`availableBlockInterventions(block)` 保护块返回 `[]`（无按钮），否则返回 `["lock","regenerate","dispute","instruct_regenerate"]`（`interventionClient.ts:17`）。
- **四动作后端端点**：
  1. **lock** — `POST /interventions/lock`（`interventions.py:120`，204 No Content）：体 `LockRequest{target_id, scope:"block"|"section", deliverable_id, project_id}`。403/404。
  2. **regenerate（章节级）** — `POST /deliverables/{deliverable_id}/sections/{section_id}/regenerate?project_id=`（`interventions.py:139`）：无体（章节级）→ `{ job_id }`；提交 `kind="report"` job。403。
  3. **dispute** — `POST /projects/{project_id}/disputes`（`interventions.py:213`）：体 `DisputeRequest{dispute_id, deliverable_id, target_kind:"block"|"fact"|"citation", target_id, reason_text, expected_version, confirmed_version?}` → `{ ledger_version }`。409 `LEDGER_CONFLICT`（detail.`current_version`）= 账本已前进，需带 `confirmed_version` 重提确认。403。
  4. **evidence（注入）** — `POST /projects/{project_id}/evidence`（`interventions.py:176`）：体 `InjectRequest{evidence_kind:"file"|"url"|"text", content_ref, note, claim_text, expected_version, user_evidence_optin}` → `{ alignment, fact_added, ledger_version, score_axis, user_evidence_verdict_optin, attempts }`。409 `LEDGER_CONFLICT`（自动重放 ≤3 耗尽）。403。
- **交互流**：
  - 乐观锁 409 确认流（dispute）：前端捕获 409 → 拿 `detail.current_version` → 显示「账本已前进至版本 {n}，确认后重提」→ 二次带 `confirmed_version` 重提（`BlockInterventionPanel.tsx:82` 已实现此流）。
  - regenerate 走 SSE：拿到 `{job_id}` 后复用 `openJobStream(jobId)` 流式挂载重写状态（`interventionClient.ts:78`：regenerate 类一律转交 openJobStream，不另建 SSE）。
  - evidence：成功后只展示后端回值 `alignment`/`fact_added`/`ledger_version`/`attempts`，前端不判定对齐/是否成 fact（`EvidencePanel.tsx:10` 注释）。
- **未来接口缝**：三个面板挂载点（可干预交付物页）；干预层文案（锁定/再生成/争议/账本冲突）目前硬编码中文未走 i18n（`BlockInterventionPanel`/`EvidencePanel`），i18n 回填另起一卡。
- **本屏状态元素**：
  - 保护块不渲染干预按钮（显示"受保护·只读"）。
  - evidence 注入结果按后端回值展示（`alignment` / `fact_added` / `ledger_version`），前端不判定；`alignment == "partial"` 标"部分支持、未成事实"。

### 2.9 指令式重生成（块级，自然语言指令）

- **是什么**：对单个块输入自然语言指令 → 只重生成该块（保护块整框不渲染）。这是"指令改"的产品形态（替代 tiptap 富文本编辑，决策①）。
- **现状**：端点【已建·未挂载】；前端 `InstructionRegenerateBox`【已建·未挂载】。唯一完整走 i18n 的干预组件。
- **后端端点**：复用 regenerate 端点 + 带体 —— `POST /deliverables/{deliverable_id}/sections/{section_id}/regenerate?project_id=`，带 JSON 体 `{block_id, guidance}`（`interventions.py:157-168`）→ `{ job_id }`。有 `block_id` → `action=regenerate_block`（块级）；无体 → `regenerate_section`（章节级，向后兼容）。
- **交互流**：

## 四、字段驱动的状态呈现规则

> 每条规则给"后端支撑字段 → 前端呈现"。字段来自 `/blocks` 响应或 verdict 响应，前端按字段值呈现（不自行判定）。

### 规则 1：结论与引用溯源
- **支撑字段**：`Citation{citation_id, doc_id, locator, quote_span}`（`models.py:256`）；正文 `CitationMark{citation_id}`；`Claim.confidence: "cited"|"speculative"`（有引用即 cited）；verdict `key_citation_ids`。
- **前端呈现**：每个 `cite` 内联标记呈现为可点引用角标；点击调用引用取数接口（须新增，后端未建）获取 `quote_span`/`doc.url`/`locator` 并展示短引文原文。`quote_span` 为 `None` 时显示"无引文段落"。无 `citation_ids` 的句子不呈现为有引用。

### 规则 2：needs_review（advisory / blocking 区别）
- **支撑字段**：`Block.needs_review/review_reason/review_severity`；`ReviewSeverity="blocking"|"advisory"`；`ReviewReason="fact_changed"|"fact_removed"|"fact_disputed"`（`fact_removed`=blocking，其余 advisory）。
- **前端呈现**：
  - `review_severity=="blocking"`（仅 `fact_removed`）：阻塞标，阻止导出/终稿，显示"引用的依据已被移除，须处理"。
  - `review_severity=="advisory"`（`fact_changed`/`fact_disputed`/正文裸数字软标）：提示标，可折叠，不挡导出。
  - 导出命中 409 `EXPORT_BLOCKED` 时用 `detail.blocking_block_ids` 高亮待处理块。
  - advisory 与 blocking 区分呈现。

### 规则 3：speculative 降权标
- **支撑字段**：`WhyNow.speculative: bool`（evidences 空→True）；`Claim.confidence=="speculative"`。
- **前端呈现**：Topic 卡读 `why_now.speculative`——true 标"推测（无证据支撑）"并抑制溯源，false 展示 `evidences[]`。结论句 `confidence=="speculative"` 呈现为降权/未核验。按字段值呈现。

### 规则 4：gap_notice 留白（缺口标注）
- **支撑字段**：`GapNoticeContent{hints_ref}`；`GapHint{missing_what, cause:"missing_data"|"missing_permission", suggested_sources, action:"search"|"ask_user"|"upload"|"request_permission", target_count, required_scope}`；verdict 的 `gaps[]`。
- **前端呈现**：
  - Gate 视图 `verdict.gaps[]` 直渲，按 `cause` 分两类、按 `action` 决定入口按钮：
    - `missing_data` → 展示 `suggested_sources` + 动作（search/ask_user/upload）。
    - `missing_permission` → 展示 `required_scope` + "请 owner 授权"（request_permission），与"缺资料"区分（缺权限不呈现为缺资料）。
  - 报告正文 `gap_notice` 块：目前只有 `hints_ref`（无解引用端点）→ 渲染为"留白/缺口"占位并保留取数位，不以生成文字填充。

### 规则 5：保护块只读
- **支撑字段**：`Block.locked/author/user_modified`；保护条件 = `locked ∨ author=="user" ∨ user_modified`（`isProtected`）。
- **前端呈现**：保护块不渲染编辑/删除/regenerate 控件，仅只读展示。三字段都在 `/blocks` 响应里，按值判定。`declaration` 类恒 `locked=true`（决策边界声明），钉在质量卡上方，不提供编辑。

### 规则 6：chart 零计算（按后端数据渲染）
- **支撑字段**：`ChartContent{chart_id}` + `ChartSpec{chart_id, chart_type, derived_from}`（`derived_from` 必填不许编）。
- **前端呈现**：前端只有 `chart_id`，画图须调图表取数接口（须新增，后端未建）获取数据。按返回数据点绘制，不做数值聚合/计算；`derived_from` 是可审计出处链，前端可展示"本图数据来自：{derived_from}"。当前无端点 → 渲染占位并保留取数位。

### 规则 7：verdict 状态（D_insufficient / disputed / partial）
- **支撑字段**：`Verdict` 四值；`VerdictResult`；`FactStatus="frozen"|"disputed"|"retired"`（新生成只从 `frozen` 池取）；`Alignment` 的 `partial` 不升 Fact；`ClaimSpan.disputed_mark`。
- **前端呈现**：
  - Gate 视图按 `verdict.verdict` 展示最高档，`all_satisfied` 提供可展开的"同时命中"。
  - `D_insufficient` 展示非空 `gaps`。
  - verdict 零猜测失败 → job `failed` → 显示"无法判定"。
  - 引用的 fact 若 disputed，其块带 advisory 标 + `disputed_mark` 标记，显示"依据存在争议"。新生成内容不引用 disputed/retired fact（后端已排除）。

### 规则 8：三通道分渲（Fact / PriceCell / ProfileRef）
- **支撑字段**：表格 `TableCell = text|fact{fact_id}|price{price_entry_id, quantity}`；段内 `ProfileRef{field_path}`；后端 `validate_channels` 强制不混（FactCell 落价格域/PriceCell 落 fact 域/裸数字/裸 profile 值均拒稿）。
- **前端呈现**：表格单元按 `cell.kind` 分派，各通道分别渲染：
  - `fact` → 按 `fact_id` 取 Fact（可溯源事实）。
  - `price` → 按 `price_entry_id` + `quantity` 取 PriceEntry（预算数字，可展示 source/年份 `PriceEntry.stale_after_months`）。
  - 段内 `profile` → 按 `field_path` 取 Profile 字段值（涉我内容）；缺失则留白（对应 GapHint）。
  - 三类各自的值解引用端点当前未提供（`/blocks` 只给 ref），前端为三通道分别留独立取数位。

### 状态字段清单（前端按值呈现的不确定性/权限/复现字段）

## 六、附：回接后端时的工程注意

1. **两个 base-URL 环境变量名未统一**（回接时两个都要设）：
   - 客户端页面（`/demo`、`/jobs/[id]`）走 `API_BASE = process.env.NEXT_PUBLIC_FLINT_API ?? ""`（`web/lib/apiBase.ts:3`）。
   - L0 服务器组件 `/deliverables/[id]` 走 `process.env.FLINT_API_BASE ?? ""`（`app/deliverables/[id]/page.tsx:14`，不同变量名）。
2. **无根首页**：`web/app/` 下只有 `demo`、`jobs/[id]`、`deliverables/[id]` 三个 page + layout；无 `app/page.tsx`，访问 `/` 无路由。正式版 `/plaza`、`/workbench`、`/gate` 路由均未建（三界面只活在 `/demo` 串联内）。
3. **运行态装配缺口**：只有 views+combo+analysis 在跑；回接前端全功能前，需一个生产装配点把 compose/deliverables/pack/interventions/categories 也挂上（扩 `demo_server.build_app()` 或新建生产 app）。
4. **鉴权占位**：所有写操作前端目前把 `userId` 写死 `"self"`（干预组件）/ 由 demo 中间件注入 `demo-user`（`X-User-Id` 缺省时）。回接真登录时替换（见 3.9）。
5. **SSE 统一入口**：所有流式（analysis 进度、regenerate、指令重生成）都复用 `openJobStream(jobId) → /jobs/{id}/events`（id=seq、data=payload JSON、Last-Event-ID 续订）。regenerate 类端点回 `{job_id}` 后一律转交 openJobStream，不另建 SSE。
6. **乐观锁**：dispute/evidence 带 `expected_version`；409 → 拿 `detail.current_version` 让用户确认/提示。
7. **前端零计算的落点**：chart（占位）、price（quantity 原样）、plaza 排序（后端已排）、gate verdict（直取）、topic.speculative（后端定）——均按后端数据呈现，无前端判定。
8. **待修 TS 类型**：`viewsClient.ts` 把 verdict 的 `constraints_checked` 误标为 `boolean`，后端实为 JSON 对象（rule_a/b/c 结构）——回接 Gate 视图时修正。
