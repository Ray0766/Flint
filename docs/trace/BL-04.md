## 4. 最要紧的一条：没有实测分词器时，tokens 数就是「没有」

`value is None`——**不是 0，也不是拿汉字数顶上**。顶上去的那一刻，一个从未被
任何东西验证过的数就成了下游眼里的事实。

- `conversion_factor()` 在任一侧未标定时**抛**，NEVER 返回一个能被误用的数；
- `compare()` 的系数位置写「未定（原因）」，`delta` 写 `None` 而**不是 0**——
  0 会被读成「两种基准一样」，那是本模块最想避免的误读；
- `basis_note()` 把「未标定 → 跨基准比值 report_only」**成句**写进输出：
  字段要人去查，句子会被读到。

## 5. 两种基准各跑一遍同一份样本（acceptance③）

### 5.1 今天的生产实况：差值**算不出来**

```
CLAUDE.md（vibe_pack）        cjk_chars=2127  tokens=None  delta=None  report_only=True
docs/答作率门槛说明.md        cjk_chars=859   tokens=None  delta=None  report_only=True
未定（换算系数未定：['tokens'] 侧没有实测分词器。）
```

**「今天算不出这个差值」本身就是一个结论**：仓里没有任何生产模型的分词器可用
（`transformers` / `tokenizers` 装了，但本机 HF 缓存只有 CLIP 与 LISA，
没有 bge-m3、没有任何 Claude/DeepSeek 分词器；下载属外网取模型，本卡不做）。
所以**现在仓里任何 tokens↔汉字的比较都没有依据**。

### 5.2 量级参照：注入本机已缓存的 CLIP BPE（**不是生产模型的分词器**）

```
CLAUDE.md              cjk_chars=2127  tokens=9834  delta=7707  tokens_per_char=4.623
docs/答作率门槛说明.md  cjk_chars=859   tokens=4045  delta=3186  tokens_per_char=4.709
```

**这两个数怎么读**：CLIP 的 BPE 对中文是**逐字节**切的，所以 4.6 这个比值是
CLIP 特有的，与 Claude / DeepSeek 那类带 CJK 词表的分词器（通常远低于此）**不是一回事**。

它能说明的只有一件事，而这件事正是本卡要说的：
**两种基准差的不是几个百分点，是数倍，而且倍数随分词器而变。**
——所以既不能混着比，也不能拍一个系数。owner 要选基准，看的就是这个「随分词器而变」。

| 变异 | 抽掉什么 | 结果 |

**变异② 为什么能活**：今天这两个条件恰好总是同时成立——没有分词器 → 既未标定、
又没有数。所以改成只看 `value` 时，所有既有用例的行为一模一样。

**但它们不是一回事**：哪天有人写一个「估算器」交出
`Measurement(value=1234, calibrated=False)`，只看 `value` 的守卫会拿这个从未被验证过的数
算出一个系数——**而那正是本模块唯一要拦的事**。补
`test_an_uncalibrated_measurement_that_does_have_a_number_is_still_refused`
（手工造一个「有数但未标定」的计量），重考变异② → **1 failed**。

这是本批第四次同型：**判据钉在了「今天恰好等价的那个条件」上，而不是真正要守的那个**。

六次变异后 `eval/unit_basis.py` 的 sha256 与变异前逐位相同。

## 7. 要 owner 定的那一句（owner_review）

本卡**没有替 owner 选基准**，也没有改任何既有度量器的单位。摆在桌上的是：

1. **选哪种基准作为报告的默认口径**（`cjk_chars` 与 `tokens` 各有主场：
   前者对人类读者的五套模板更自然，后者对 vibe_pack 与 40k 预算是原生单位）；
2. **要不要取一个生产模型的分词器进来**（取了，`tokens` 侧才能标定；
   取哪一个又决定了系数——§5.2 说明系数随分词器数倍地变）；
3. 在 1、2 定之前，所有跨基准比值**保持 report_only**（本模块已按此实现）。
