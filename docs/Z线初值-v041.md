# Z 线（任务一次通过率）初值依据（Z-01 · 2026-08-04）

**结论先写**：Z 线初值 **0.95**。度量器从 `report_only` 升为**可判定**——
判 pass 或 fail，不再只报数。

**owner 指示（2026-08-04）**：NEVER 因为本地条件通不过就把线一直悬着——
**线先画上**，达不到是另一件事。

**这条线一半来自权威、一半来自本项目实测**，下面分开写。分不开的话，
读的人无从判断它是行业口径还是我们自己的成绩单，而这两者被质疑时的答法完全不同。

---

## 一、权威那一半：0.95 是 DORA elite 档换算出来的

| 口径 | 内容 | 出处 |
|---|---|---|
| DORA 2024 变更失败率 | elite 档（约前 20% 的团队）的**变更失败率 ≤5%**，即一次成功率 **≥0.95** | https://www.opslevel.com/resources/tl-dr-key-takeaways-from-the-2024-google-cloud-dora-report |
| 该指标的定义 | 变更失败率 = 导致服务降级或需要补救（热修 / 回滚 / 打补丁）的变更占比 | https://getdx.com/blog/dora-metrics/ |
| 分档结构 | 报告把团队分成 elite / high / medium / low 四档，稳定性面的关键指标就是它 | https://octopus.com/blog/2024-devops-performance-clusters |

**为什么这个口径搬得过来**：DORA 的「变更失败」= 这个变更**没能一次做对**，
要回头补救。本仓的 oneshot 口径是「任务首个 verify 即绿为一次通过，
返工后通过不计」——两者问的是同一件事：**一次做对的比例**。

**为什么不是别的口径**：制造业的 FPY（First Pass Yield）也量一次通过率，
但它的分母是物料批次，良率线随工艺而定，没有一条跨行业可搬的数。
DORA 是**软件交付**领域公开分档且给了具体百分比的那一份，所以用它。

## 二、本项目实测那一半：n≈197，零 review_failed

| 批次 | 样本量 | 观测 |
|---|---|---|
| M4 出口 | **19** 卡 | rate = 1.0（当时记的就是 `report_only`，见 `docs/M4-出口报告.md` 第 3 行） |
| v0.4 台账 | **122** 卡 | `docs/progress-v04.jsonl` 里 `review_failed` **0 次** |
| v0.4.1 第 2 批 | **56** 卡（本文写时） | `docs/progress-v041.jsonl` 里 `review_failed` 0 次；1 张卡（K1-01）有跨轮重入痕迹，**按未一次通过计** |

合计 n ≈ **197**，观测失败 0~1 次。

**这份实测有两个已知的弱点，照实写下来**：

1. **台账记的是事件，不是 verify 次数**。「首个 verify 即绿」这件事没有直接记录，
   只能用 `review_failed` 与重复 `started` 当代理。代理会**低估**失败率——
   一张卡在同一轮里 verify 红了两次再绿，台账上看不出来。
2. **样本不是随机抽的**：全是本仓自己的卡，且执行者是同一个 worker。
   跨项目的可比性未知。

## 三、误差：三法则给的 95% 下界是 0.985

零失败样本不能直接说「通过率 = 1.0」。标准做法是**三法则**
（rule of three）：n 次试验 0 次失败时，失败率的 95% 置信上界 ≈ 3/n。

```
n ≈ 197  →  失败率上界 ≈ 3/197 ≈ 1.5%  →  通过率 95% 下界 ≈ 0.985
```

**0.95 落在这个下界之下**。也就是说「本项目超过这条线」不是运气好，
是样本量撑得住的结论——把线画在 0.95，本项目**有余量地**通过。

---

## 四、为什么不画 1.0

实测确实是 1.0，把线画在 1.0 看起来更严。但：

1. **1.0 是没有余量的线**：20 张卡里返工一次就判 fail；
2. **返工在本仓是被鼓励的**：`CLAUDE.md#S7` 的返工环写着「verify 或 review 失败 →
   按意见修改重跑」，只有**同一原因连续 2 次失败**才升级。把线画成 1.0
   等于把「返工」定义成「不合格」，与那条纪律**自相矛盾**；
3. **1.0 会把度量器变成噪声源**：一条永远在红边缘的线，读的人很快就会开始忽略它。

线画在 0.95、实测在 0.985 以上，**余量正好是给返工留的**。

---

## 五、怎么调这条线

改 `FLINT_Z_LINE` 环境变量即可（`flint/config.py#load_z_line`），**不改代码**。
写错的值会报错而不是静默回落——静默回落会让 owner 以为自己调了线，
而报告上的判定其实还是按旧线出的。

**什么时候该调**：
- 样本量涨到 500 以上且仍零失败 → 可以考虑抬到 0.98（那时三法则的下界≈0.994）；
- 出现连续两批不达标 → **先查是不是卡拆得太大**（`estimate_cycles > 2` 是拆分信号），
  而不是先把线放低。**放低线是最后一步，不是第一步**。
