# I18N-02 trace — i18n 扫描器 + 组件目录 key 化 @2026-08-02

## 1 一次测量错误（先记下来）
初次用 `grep -rlP "[\x{4e00}-\x{9fff}]" web/components` 数中文文件，得 **0**——假阴性
（该 grep 不支持这种 `\x{}` 写法，静默返回空）。改用 Python 正则实测：**18/18 文件含 CJK**。
再按真实扫描口径（排除测试文件与注释）收敛为 **3 个源文件 / 12 行**。
**「查不到」与「真没有」是两回事**，这次差点把前者当后者。

## 2 扫描器（`tools/i18n_scan.mjs`）
- CJK 字面量：逐行扫，**剥掉注释**后再判（注释不发给用户）；
- **白名单是推进机制不是豁免机制**：白名单内文件仍逐一列出（pending），只是暂不使
  `--fail-on-cjk` 失败；扫描器在白名单非空时会打印「acceptance 要求收尾时为空——
  留一条永久豁免就等于没做这张卡」。**本卡收尾时白名单为空**（0 项）；
- **B7 静态规则**：同一行里既有 `embed|search|retriev|dedup|cluster` 语境、又引 `*_display`
  字段 → 违规。理由：引到机翻派生物会让同一个热点因译文不同被认成两个。
  实测 **0 违规**。

**DEC-008：扫描面排除测试文件**——测试里的中文是断言数据，不是界面文案；
key 化它们会让测试变成同义反复。

## 3 key 化（12 条文案 → 12 个 key）
命名 `<域>.<元素>.<语义>`（`block.action.lock` / `evidence.conflict` …），
**NEVER 把中文当 key**。zh/en 双份 messages 键集一致。

**DEC-009：走 `web/lib/i18n/t.ts` 薄封装**而不是直接 `useTranslations`——
既有 11 个组件测试直接渲染组件（无 Provider），强依赖 Provider 会逼每个测试包一层
只为「让它跑起来」的壳。薄封装两条路径取**同一份 messages**，
所以测试断言到的文案与用户看到的**逐字相同**。
key 缺失时返回 key 本身并告警，**NEVER 返回空串**（空串会让界面出现一块无声的空白）。

## 4 一处自纠
脚本插 import 时按「最后一个 `import ` 行」定位，结果插进了多行 import 的**中间**
（`import {` 与其成员之间），`tsc` 报 TS1109。已修回 import 块之后；
**注意 test 数从 69 掉到 67 时我没有当成噪音**——那正是该文件编译失败、整份测试没跑。
