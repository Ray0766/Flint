# 间歇红：怎么连跑、怎么把现场留下来

> 本文治的是一种具体的失手：**跑到一次红，却不知道红的是哪一条。**
> 那一次红于是变成「重跑一遍就好」，而下一个人从零开始。
>
> 出处：`docs/blocked/ONE-UNNAMED-FRONTEND-RED-NOT-CAPTURED.md`
> （2026-08-06 观测到一次前端红，**当时的命令只 grep 了汇总行，把用例名过滤掉了**）。

## 一、跑法

```bash
node web/scripts/repeat-tests.mjs --runs 30
# 产物：.ui-probe/frontend-red.json
```

逐跑记一条：`run` / `exitCode` / `green` / **`failed`（失败用例名）** / `summary` / `ms`。
两种形状都抓：行内 `× 用例名` 与汇总段 `FAIL 文件 > 用例`。

**脚本恒退出 0。** 它是取证工具，不是判据——
取证工具自己判红的话，「没复现」与「工具挂了」会长得一模一样。

## 二、只留汇总行是不够的

汇总行长这样：

```
 Test Files  1 failed | 73 passed (74)
```

它告诉你**有**一条红，不告诉你**是哪一条**。而下一步（复现、定位、判断
是不是同一处）全都需要那个名字。所以 `--reporter=verbose` 与
「逐跑落一份日志」两样缺一不可。

## 三、绿多少次都不等于「它不存在」

这条最容易被跳过。实测依据在 `docs/trace/FIX-04.md`：
那处间歇红是 **40 次循环里第 29 次**才复现的。

所以：

- **30 次全绿 = 「30 次未复现」**，写进单子，**单据保留开着**；
- **NEVER 写成「修好了」**，也 NEVER 关单；
- 连跑的**环境**要一起记下来：那一次红发生在 `globals.css` 被反复改写、
  Next dev server 正在监听它的时候。同一份代码在**别的环境**下跑 30 次绿，
  甚至没有覆盖当时的条件。

`docs/trace/FIX-04.md` §6 的原话：造不出稳定红时，诚实的说法是
「**没定位到**」，NEVER 是「修好了」。

## 四、抓到名字之后

照 `FIX-04` 的路子：**先把它逼成稳定红，再动手改**。
拿一次偶发红去改代码，改完那次不红了——你不知道是修好了还是这次没撞上。

## 五、判据在哪

`tests/v041/test_frontend_red_capture.py`。它里面有一条**阴性对照**：
喂一段真实形状的 vitest 输出，脚本必须抽得出用例名。

没有那一条，「30 次全绿」可能只是因为脚本根本不会抓名字——
**而那正是这张单子的由来**。

## 六、历次观测

| 轮次 | 卡 | 跑数 | 结果 | 那一轮的树 |
|---|---|---|---|---|
| 一 | `FIX-05` 收卡时偶遇 | 1 | **红 1 个文件，名字丢了** | 变异考期间，`globals.css` 被反复改写 |
| 二 | `FIX-08`（第 6 批） | 30 | 全绿，每跑 802 passed | 第 6 批收尾 |
| 三 | `FIX-15`（第 7 批） | 30 | 全绿，每跑 831 passed | 第 7 批收尾（本批又改了 `globals.css`、dev server 在跑） |

**三轮之后单据仍然开着。** 那不是拖延——是「没复现」与「不存在」不是一回事。
