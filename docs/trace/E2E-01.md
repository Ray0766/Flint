## 2. 与 `ASM-05` 那 7 条的区别（acceptance④ 点名）

| | `ASM-05` | 本卡 |
|---|---|---|
| 客户端打的应用 | `create_compose_app(...)` / `create_deliverables_app(...)`——**每族各造一个**（harness 直调） | `harness/e2e_stack.py#build_e2e_app`——**`create_app` 装配后的那一个** |
| 队列 | 真 arq | 同（两次提交各自入队、各自由 burst worker 消费） |
| gate1 | **不在链上** | **在链上**：`POST /projects/{id}/analysis` → 队列 → `run_gate1` 四步 → 判定落盘 |
| 外部源 | 组稿 provider 回放 | 组稿 provider 回放 **+** gate1 检索走 `fixtures/gate1_live/` 录制 |

**为什么这个区别要紧**：每族各造一个应用，测的是「这一族自己好不好」；
线上跑的是**并进一个应用之后**的那份路由表。`WIRE-01` 那次漏掉 51 条路由时，
各族的测试全是绿的——**没有任何判据在量装配后的样子**。

## 3. 提交那两族在可部署应用里挂不上，所以有了 `harness/e2e_stack.py`

`POST /projects/{id}/analysis` 与 `/report` 属 `analysis` / `compose` 两族，
在 `create_app` 里是 `UNWIRED_FAMILIES`（缺 `role_resolver`——本仓还没有
`users` / `memberships` 两张表，做不出诚实的角色解析）。打过去回
`503 FAMILY_NOT_CONFIGURED` 并点名是哪一族，**那是对的行为**。

夹具栈用 `lambda _u, _o: "owner"` 把这两族补上（与 `harness/demo_server.py`
同一条明知故犯的口径），并把「多出来的正好是这两族」做成判据：
`test_the_stack_is_the_deployable_app_plus_exactly_two_families` 判**等值**——
多一族要有人来确认它是不是也该进可部署应用，少一族说明鉴权补上了、这里该收。

装配走的是 `create_app` 的**同一个 `_Assembler`**：路由撞车照样 raise，
NEVER 因为「这是夹具」就少一道闸。

**没有动 `harness/demo_server.py`**：它的注释写着「owner 裁决：interventions 挂、
compose 不挂」，且它的作业派发是 `asyncio.create_task` 不经 arq——
要在 demo 栈上跑这条链就得改那条裁决与那个派发面，两件都不是本卡的事。

## 4. 本卡最该被看见的一条：主链路**在中间断成两段**

跑通之后发现：gate1 的产出与组稿的取数面**对不上**。

| 段 | 产出落在哪 |
|---|---|
| gate1 | `snapshots`：`snap-{job}-docs` / `-judge` / `-verdict` |
| 组稿 | 读 `claims WHERE deliverable_id = <analysis_id>` |

gate1 从不往 `claims` 写行（support/refute 在 judge 快照的 JSON 里）。
所以「拿判定去组稿」这一步，今天**只能靠人手种一条 claim**——
`ASM-05` 这么种，本卡也这么种。

**两段各自都是绿的，而中间那一跳没有任何判据横跨过。**
已开单 `docs/blocked/GATE1-VERDICT-IS-NOT-A-COMPOSE-SOURCE.md`，
并用 `test_gate1_output_is_still_not_the_claims_source` 把现状钉住：
哪天有人接上那一跳，**这条会红**，红的时候去关单并把「种一条 claim」那步删掉。

## 5. 一次跑通的实况

```
POST /projects/{id}/analysis  → 200，job 入队（zscore 里有它）
burst worker（注入 gate1_deps）→ 消费 1 / 失败 0；jobs.state=done；verdict 快照在
POST /projects/{id}/report    → 200，job 入队
burst worker（组稿 provider 回放）→ 消费 1 / 失败 0
GET /deliverables/{id}/blocks → 200，块型里有 paragraph（**不是只有 heading**）
GET .../render?fmt=markdown   → 200，markdown 非空
挂上 blocking 复核后再 render → 409 EXPORT_BLOCKED
全程                          → respx 零路由罩着，router.calls 为空
```

## 7. owner_review

1. **夹具栈里那句 `lambda _u, _o: "owner"`**。它与 demo 栈同一条口径，
   只在 pytest 与本机 e2e 里被调用。但它意味着**端到端判据证的是「鉴权之外的链路」**——
   鉴权补上之后，这条链要再验一次（那时 `analysis` / `compose` 应当进可部署应用，
   `extra_families()` 的等值判据会红，提醒来收）。
2. **主链路中间那一跳**（§4）：要 gate1 落 claims，还是要组稿多认一种来源？
   这是产品口径，不是接线选择——单子里两条路各写了代价。

## 8. 登记未做

1. **`fmt=pack` / `docx` / `pdf` 没跑**。本卡只跑了 `markdown` 那一路；
   `pack` 在 `create_app` 里明说不可用（503），另两种要渲染器的二进制面。
2. **SSE 进度流没验**。`GET /jobs/{id}/events` 挂上了（夹具栈里在路由表内），
   但本卡只在作业**跑完之后**查库，没有订阅过程中的事件。
3. **gate1 只跑 scripted 那一路**（与 `QUEUE-01` 同）：`fixtures/gate1_live/qwen/`
   那份双录制没接进端到端。
4. **两次消费用了两个 worker 实例**（各 burst 一次）。真实部署是一个常驻 worker
   连续消费两条——本卡没有验「同一个 worker 先后吃两种 kind」。
