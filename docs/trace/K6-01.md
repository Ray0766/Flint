## 3. 交互形态：照 Slack 的工作区切换器（卡面要求「先搜权威产品怎么做」）

| 参考 | 取到什么 | 出处 |
|---|---|---|
| Slack 工作区切换器 | **一个常驻入口（左上角）→ 点开展开成一份列表 → 点一项就切过去**；不是多层菜单 | https://slack.com/help/articles/1500002200741-Switch-between-workspaces |
| Slack 改版争议 | 旧切换器被砍后用户找不到入口，最后作为可选项**恢复**了——「入口要常驻可见」不是审美偏好 | https://tidbits.com/2023/09/21/how-to-restore-the-slack-workspace-sidebar/ |
| 多租户权限对比（Slack / Notion / Linear） | 三家都把「工作区」当**顶层容器**，切换是**整体上下文切换**，不是过滤器 | https://workos.com/blog/multi-tenant-permissions-slack-notion-linear |

**照搬了什么**：常驻入口 + 单层列表 + 点选即切。
**没照搬什么**：多层菜单与拖拽排序——多台在本产品里是「同一个人的几个思考现场」，
不是租户树；排序是等台多起来才有的问题，现在做等于替一个还没出现的问题设计。

**自己加的两条**（Slack 没有，本产品的语义要求）：
1. **最后一台不给归档**：归档掉全部会让用户落到一个没有工作台的界面，
   而那个界面在本产品里根本不存在；
2. **归档区里没有删除入口**：归档不是删除（`multi.py` 原话「归档的台仍然存在、
   仍可翻回」），数据删除是 owner 人审节点，v0.4 内没有这条路径。

## 4. GRAPH-16 的纪律怎么守的（acceptance③）

状态只有两个正交的键：`currentId`（在哪台）与 `showArchived`（归档区展开与否）。
`workbenchTabsStore.ts` 已经为「放一个 mode 键进来」付过一次代价
（它与页签、折叠态成为两份真相），这里不再付第二次。

判据两条，**都落在代码面**（剥掉行注释）：组件里没有 `mode` 键、
`WorkbenchSwitchState` 的键恰为那两个。剥注释是必须的——
组件注释里逐字写着「NEVER 出现 mode 键」，扫原文会把「禁掉它」当成「用了它」。

组件里的三处 JSDoc 也改成了行注释：本仓的扫描器对跨行块注释有已知假阳性
（DEC-013 / 卡 I18N-09），而「零 CJK 字面量」那条判据正是靠剥行注释实现的。
`workbenchTabsStore.ts` 里有同款处置与同款理由。

## 6. 变异考：十三个，一个先活了下来

组件面（跑 vitest）：

| 变异 | 结果 |
|---|---|
| ① 归档的台也进切换列表 | **3 failed** ✓ |
| ② 切到当前台也触发 | **1 failed** ✓ |
| ③ 最后一台也给归档 | **1 failed** ✓ |
| ④ 当前台不标 `aria-current` | **1 failed** ✓ |
| ⑤ 归档区不折叠就露出恢复键 | **1 failed** ✓ |
| ⑥ 空台时入口消失 | **1 failed** ✓ |
| ⑦ 文案写死不走 i18n | **1 failed** ✓ |
| ⑧ 塞一个 mode 键进状态 | **1 failed** ✓ |

样式面（跑 pytest）：

| 变异 | 结果 |
|---|---|
| ⑨ 入口没有最小高度 | **1 failed** ✓ |
| ⑩ 底色写裸值 | **1 failed** ✓ |
| ⑪ token 名写错（`--surface-carddd`） | **11 passed** ✗ → 补判后 **1 failed** ✓ |
| ⑫ 当前台无视觉标记 | **1 failed** ✓ |
| ⑬ 少用一个 token（间距写没了） | **1 failed** ✓（补判顺带） |

**⑪ 为什么能活**：判据核的是一张**手写的 token 清单**与 `_ds` 的对照——
清单没变，globals.css 里用的名字变了，于是断言照样绿。而 CSS 对写错的
`var(--x)` **不会报错**，只是静默取空值落回 UA 默认样式。
修法：token 名**从 globals.css 里真正用到的那些上取**（正则抓 `var(--…)`），
再与 `_ds` 对照；另加一条下界（该用到的一个都不能少），⑬ 验的就是这条下界。

**一条要记的边界**：像素面的判据**管不了 CSS 变异**——`.ui-probe/*.json`
是一次取证的产物，变异时它不会重新生成。所以样式面的判据必须自己站得住，
不能指望像素面兜底。

十三次变异后三个产物文件的 sha256 与变异前逐位相同。

## 7. 像素取证与一条新立的卡

跑法（`_ds` 经 dev server 取，栈要在跑）：

```
C:\pwenv\Scripts\python.exe tests/v041/test_workbench_switch.py
→ styled.ok=True  unstyled.ok=True
```

**阴性对照与 FB-02 不是同一个形状，这一点花了一轮才认清**：
FB-02 守的是空 span（没规则就 0×0，直接红）；本卡守的是**带文字的 button**，
浏览器给它默认样式，抽掉规则**照样看得见**（实测 `unstyled.ok=True`）。
照抄 FB-02 的对照会得到一条**永远绿的阴性对照**——那比没有对照更糟，
它看起来像验过了。改钉在这条规则真正买到的东西上：**可点区域高度 ≥ 24px**
（`--sp-5`），抽掉后实测 23px；外加底色必须从 UA 灰 `rgb(240,240,240)` 变成
`_ds` 的 `--surface-card`。

**顺带发现一件更大的事**：两个主题量出**完全相同**的一组数
（`rgb(27,42,46)` / `rgb(247,248,243)`，96×29，一位不差）。
查 `_ds`：**没有 `prefers-color-scheme`，也没有 `data-theme`**——这套设计系统
只有一块调色板，而探针切主题走的是 `color_scheme`。也就是说 EYE-02 的
「明暗两主题」对任何由 `_ds` 上色的元素**目前是在把同一组颜色判两遍**。
不误判，但证不到它字面上声称的那件事。立卡
`docs/blocked/EYE-02-TWO-THEMES-MEASURES-ONE.md`，三条路留给 owner 选。
**本卡不宣称「暗色下也验过了」**——因为没验过。

## 9. owner_review：三件要 owner 拍板的

1. **入口放在哪**：本卡交的是**组件**，没有把它挂进任何页面。Slack 放左上角，
   本产品的壳是 `web/views/workbench-shell/`——挂进去要动壳的布局，
   **超出卡上 outputs**，而且位置是设计判断。

   所以本卡**没有打开它**——打开一个挂不上的入口比关着更糟。
3. **暗色板要不要做**（见 §7 与那张 blocked 卡）：这关系到 EYE-02 的
   「明暗两主题」判据现在到底证到了什么。
