## 四、技术问题清单（按严重度排，每条带出处与修法规模）

### T1 · 首次组稿的默认生成器是占位，产不出正文 —— **最严重**
**事实**：`flint/jobs/compose.py:133` 的 `_default_generator` 只返回**一个 heading block**，正文内容 = `spec.section_id` 这个字面量。
**关键点**：全仓 `generator_factory=` 只有**一个赋值点**（`flint/jobs/compose.py:142`），赋的就是这个占位。真正的 LLM 生成器 `flint/compose/llm_generator.py` 只被 `flint/jobs/regenerate_job.py:56` 用上——那是**单块重生成**路径。
**后果**：走生产 compose job 生成一份报告，得到的是一串空标题；正文只能靠事后逐块 regenerate 补。
**修法规模**：把 `llm_generator_factory` 接进 `build_offline_compose_deps` + 一条端到端断言。**2~4 cycles（±40%）**，误差来自 provider 注入与 guidance 装配面。

### T2 · 没有 worker 消费组稿作业，主链在编排层断开
**事实**：`PgJobRunner` 是状态机 + 权限层，实际执行靠**注入的 enqueue 钩子**（`flint/jobs/runner.py:97`）。全仓唯一接了钩子的是 `harness/demo_server.py:191`，而它**只接 `gate1_analysis`**——这句是仓库自己写的：`harness/demo_seed_report.py:6`「没有 report 组稿 worker（demo_server 的 enqueue 只接 gate1_analysis）」。`run_compose` 的调用方只有它自己的 CLI `__main__`（`flint/jobs/compose.py:359`）与测试。
**后果**：`POST /projects/{id}/report` 能建 job、能返回 job_id，**没有任何进程会去跑它**。
**修法规模**：arq worker 装配 + kind→handler 表。**3~5 cycles（±40%）**。

### T3 · demo 里的报告数据是脚本播种的，不是真跑出来的
**事实**：`harness/demo_seed_report.py` 自述——因为 T2，前端拿 `GET /deliverables/{id}/blocks` 只会 404，所以该脚本**直接往 store 写 Block**，`deliverable_id` 前缀 `del-demo-fixture-` 作标记。
**要说公道话**：这份脚本自己把边界写得很清楚（不冒充模型产出、不自动跑、只 opt-in），它是诚实的脚手架而不是造假。**问题不在它，在于它现在是唯一能让报告页有内容的路径。**
**修法**：T1+T2 修完即自动消解。

### T4 · 两套前端并存，产品面只有 3 屏
**事实**：`web/`（DEC-007 认定的唯一工程根）只有 **3 个 `page.tsx`**；`V0 files 前端设计/` 有 **16 个**，但那里 **0 个测试文件**、64 个依赖（含 `expo` / `expo-gl` 这类 React Native 残留与 `@vercel/analytics`，后者与 DESIGN-20「产物 NEVER 向外部要东西」正面冲突）、无 next-intl、无 `_ds`。
**后果**：护栏与页面分居两地——`web/` 有判据没界面，V0 目录有界面没判据。
**待 owner 决策**（我已在前一轮给了建议与反方，此处不重复）。

### T5 · 定时批未装配
**事实**：`flint/jobs/sched.py` 只有 cron 骨架，注释写明「arq cron 于 worker 进程装配」；`flint/jobs/revalidation.py` 同样把注册归给部署面。
**后果**：「四热点源日更」这个 S1 里的核心承诺，当前**没有任何东西在定时触发**。
**修法规模**：与 T2 同批，**+1~2 cycles**。

### T6 · 支付与免费额度：零实现
**事实**：全仓搜 `stripe|alipay|wechat_pay|支付|订单|free_quota|免费额度`，**命中 1 处，且是一句注释**（`flint/analysis/deep_job.py:25`「NEVER 在这里直接调支付」）。真正存在的只有计费落点参数化（缺落点时 `ChargeLandingMissing` 抛在 submit **之前**——这个顺序是对的）。
**后果**：`CLAUDE.md` S1 把「支付（免费额度 + 按次）」写进 V1 商用 MVP 范围，这一块**从未开工**。
**前置**：K7（免费/付费路线）与 K8（汇率与多币种分档）都还空着，定价没定就没法开工。

**后果**：K1 空 = 广场目前没有真实的九国源可拉；这不是 bug，是输入缺位。

## 五、数字质量的真相（别被 1840 全绿误导）

统一判官（claude-sonnet-5）重判三家产出，同一 held-out 题库，report_only（`docs/M4-出口报告.md#6.2`）：

| 被判产出 | 作答率 | 配比 worst-dev |
|---|---|---|
| claude-sonnet-5（付费 · repair-on） | **0.434** | 0.206 |
| gemma4:31b（免费） | 0.395 | **0.243** |
| qwen3.6:27b（免费档默认） | 0.357 | 0.589 |

**怎么读这三个数**：
- 原始的 0.90 绝对门**已作废**（出处已断），改成相对付费参照门槛 `free ≥ 0.434 × 0.85 = 0.369`。
- 配比 ≤0.15 硬门也已依外部权威作废、改 best-effort；**免费档 repair-off 口径下 0.243 未达**，这条 M4 出口报告里如实记着「当前未达」。
- 免费档默认选 qwen3.6:27b 的依据是**权威中文榜**（C-Eval 92.8 vs 81.4），不是内部覆盖率——而内部覆盖率恰好相反（gemma 0.395 > qwen 0.357）。这处分歧报告里明写着没藏。
- 天花板本身只有 ~0.43，说明**这把内部尺子是窄代理，不是质量的真身**。

**给 owner 的白话**：这三个数不代表「报告写得好不好」，它们量的是「逐节答问覆盖」。真正的质量门是那些**结构性判据**（每个数字有出处、模板未固化拒导出、空假设边阻断），那些是二值的、可执行的，而且已经落码了。

## 八、我的判断

三件事，按这个顺序：

1. **先接主链（T1/T2/T5）**，6~11 cycles。理由：护栏、判据、闸门都已成体系，但它们守的是一条**现在还没有流量的管道**；判据再多，没接上就一条都不生效。
2. **同时开终检**（T10）——只读、不改实现，与接线不冲突，且越早发现卡面问题、返工面越小。
3. **前端归并（T4）等你拍**，拍完再动手；在那之前 worker 不要碰任何一个前端目录。

支付（T6）与源清单（T8）属于**没有你的输入就无法开工**的那一类，不占执行侧的排期。
