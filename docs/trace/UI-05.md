## 2. 两条来自 v2 2.15 的硬规则

### 2.1 stale 只由后端说了算，而且有**三种**值

v2 原话：「stale 判定来自后端 `Revalidator` 统一口径，**前端 NEVER 自行按时间戳推断**」。

按时间戳推断看起来总是对的：三个月前的收藏「显然」旧了。可事实一个字没变时，
那个标记只让用户白重跑一次；而昨天的收藏也可能因一次事实移除而彻底失效。
所以本组件里**一处日期运算都没有**（判据扫 `Date` / `now` / 与时间字段的大小比较）。

再往前一步：`snapshot_stale` 有 `true` / `false` / **没判过** 三种。
**没判过 NEVER 显示成「最新」**——那是一句我们没有资格说的话。
三种各带各的 `data-favorite-stale`，判据断言三个标记互不相同。

（BE-08 那边同一件事的形态是 `POST /favorites/{id}/staleness` 的
`status: "not_checked"` + **连 `snapshot_stale` 这个键都不给**。前后端同一条纪律。）

### 2.2 列表 NEVER 出现空壳

v2 原话：被收藏对象的 snapshot 受冻结保护（E2-P1），
列表 NEVER 出现「已收藏但内容已被清理」的空壳。

后端那侧靠**内嵌**保证（`flint/fav/store.py`：收藏时把内容抄一份带走）。
前端这侧的责任是：万一真拿到一条没有内容的，**把它标出来**——
渲染成一张空卡片，看起来像「这条收藏没内容」，而真相是内容丢了。
