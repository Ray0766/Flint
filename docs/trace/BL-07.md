## 3. 缺的是「取」那一半

`UnwiredKindReason` 的原话：「`flint/jobs/revalidation.py` 只有扫描器
`run_revalidation_scan`（它负责 submit kind=revalidation 的作业），仓里还没有
消费这些作业的 per-job 消费者。」

翻译成后果：**扫描器每天 04:00 往队列里塞作业，而没有人取**。作业停在 `queued`，
「到期复核」这件事在系统里看起来「有」——jobs 表里有行、扫描器有日志——
**实际一次都没跑过**。

## 4. 三族锁，构造上撞不了

| 锁 | 键 | 出处 |
|---|---|---|
| 日更批次 | `lock:daily_ingest:{day}:{batch}` | `flint/jobs/sched.py`（既有） |
| 复核扫描 | `lock:revalidation_scan:{day}` | 本文件（既有） |
| **复核单项** | `lock:revalidation:{project_id}:{due_on}` | **本卡** |

`test_no_input_can_make_the_two_key_families_collide` 拿几组容易撞的输入
（`project_id="am"`、`project_id="2026-08-04"`、`batch="p:1"`）交叉造键，
断言两族**不相交**——不是「今天不撞」，是前缀不同所以撞不了。

撞上的后果很具体：一次日更批次会把当天的复核锁顶掉（或反过来），
而两者都会以为自己拿到了锁。

**释放走令牌校验**（与 `sched.BatchLock` 同口径的 Lua）：令牌不符是 no-op，
不误放他人的锁。

## 5. 判定**委托**，而且用属性钉住

`default_revalidator.__wrapped__ is build_report` —— 判定件的出处写在**函数对象**上，
守卫核对的是对象身份，不是源码字符串。

**为什么不扫源码**：源码字符串会被注释骗（本仓踩过十次同型）。
`__wrapped__` 是运行时事实，注释改不动它。

本壳自己**不判**任何东西：`test_the_consumer_never_writes_its_own_stale_judgement`
禁掉四类痕迹（`VerdictShift(` / `A_infeasible` / `B_red_ocean` / `_VERDICTS`），
`test_the_only_shift_constructor_is_still_the_single_one` 再确认唯一构造点仍在
`flint/revalidate/run.py`。**同一件事两个真相是本仓的老病**，这两条一起守它。

`default_revalidator` 被直接调用时**抛并说明**：它需要 `Gate1Deps`
（provider + searcher），调用方 MUST 注入。抛比返回一个空结果好——
返回空结果等于「复核过了、没发现问题」。

## 6. `running` 不是这个仓的 job 状态

首版消费者把状态推成 `running`，真库当场 `CheckViolationError`：
`ck_jobs_state` 只认 `queued / retrieving / judging / drafting / validating /
done / failed / cancelled`（`migrations/0002_job_tables.py`）。

改成 `queued → retrieving → done`：复核 = 完整 gate1 重跑，**第一步就是检索**。
中间三相不逐个上报——判定件是委托出去的，它不回报相位（登记见 §9-2）。

**这次红得好**：如果测试只跑内存态、不碰真库，这个错会一直留到生产。
